# خطة — الدخول بالبريد وكلمة المرور، إلى جانب الجوال والـOTP

التاريخ: 2026-08-27

---

## الوضع الحالي — مقيس لا مفترَض

| ما فحصته | النتيجة |
|----------|---------|
| طريقة الدخول الوحيدة اليوم | جوال + OTP عبر Authentica |
| حقل البريد | **لا يوجد** في `Employee` ولا في `CharityUser` |
| `Employee.password` | موجود، **إلزامي**، ومجزَّأ بـbcrypt |
| هل يُتحقَّق منه عند الدخول؟ | **لا** — `compare` غير مستدعاة في المشروع كله |
| `CharityUser.password` | لا وجود له إطلاقًا |
| الحسابات | ١٢ موظفًا (كلهم نشطون) · ١٤ مستخدم جمعية |
| موظفون لديهم تجزئة قديمة | **١٢ من ١٢** |
| مكتبة إرسال بريد | **لا توجد** |
| تحديد معدل المحاولات | موجود (`checkRateLimit`)، **في الذاكرة** |

### حقيقتان تحكمان الخطة

**١. التجزئات الاثنتا عشرة القائمة عديمة القيمة ويجب طرحها.** وُضعت أيام الدخول بالجوال، ولم يستعملها أحد منذ زمن، ولا أحد يذكرها. الإبقاء عليها كـ«كلمة مرور جاهزة» يعني أن يجد ١٢ حسابًا نفسه بكلمة مرور لا يعرفها صاحبها ولا يعرف أنها تفتح شيئًا — وهذا أسوأ من غيابها. **تُمحى، ويضع كل موظف كلمة مرور جديدة بنفسه.**

**٢. لا يوجد إرسال بريد، ولا حاجة إليه.** «نسيت كلمة المرور» لا يحتاج بريدًا هنا: **الجوال والـOTP يبقيان طريقًا كاملًا للدخول**، فمن نسي كلمة مروره يدخل برمز ثم يضبط واحدة جديدة من ملفه الشخصي. هذا يُغني عن بناء بنية بريد كاملة، ويجعل القفل خارج الحساب مستحيلًا.

## أولًا: قاعدة البيانات

### التغيير

```prisma
model Employee {
  phone    String  @unique
  /// بريد الدخول. اختياري: من لم يضبطه يدخل بالجوال والـOTP كما كان.
  email    String? @unique
  /// تجزئة bcrypt. null تعني أن صاحبها لم يفعّل الدخول بالبريد بعد.
  password String?
}

model CharityUser {
  phone    String  @unique
  email    String? @unique
  password String?
}
```

### لماذا `null` مسموح — وهذا جوهر الخطة

جعل الحقلين إلزاميين يوجب تعبئة ٢٦ حسابًا قبل النشر، وأي حساب يفوتنا **يُقفل خارج النظام**. أما `null` فتعني ببساطة «لم يفعّل الدخول بالبريد»، ويبقى الجوال يعمل. **الترحيل لا يستطيع أن يقفل أحدًا مهما أُهمل.**

و`String? @unique` في Postgres يسمح بعدة `NULL` ويمنع تكرار القيم الفعلية — وهو المطلوب بالضبط.

### الخطوات بالترتيب

| # | الخطوة | ملاحظة |
|---|--------|--------|
| ١ | `email String? @unique` للنموذجين | إضافة بحتة |
| ٢ | `password` من `String` إلى `String?` | تخفيف قيد، لا فقدان |
| ٣ | `password` جديد لـ`CharityUser` | إضافة بحتة |
| ٤ | `UPDATE "Employee" SET password = NULL` | **يمحو ١٢ تجزئة ميتة** |
| ٥ | معاينة `migrate diff` قبل كل `db push` | كالعادة |

الخطوة ٤ هي الوحيدة التي تمسّ بيانات، ولا تُنفَّذ إلا بعد أن يعمل مسار «ضبط كلمة المرور» — وإلا بقي الموظفون بلا طريق لتفعيلها.

## ثانيًا: من يضبط ماذا

ثلاثة مسارات، وكل واحد يحلّ مشكلة لا يحلّها الآخر:

| المسار | من | لمن | لماذا يلزم |
|--------|-----|-----|------------|
| **أ. عند الإنشاء** | مدير الموظفين / مدير الجمعية | حساب جديد | حتى لا يُولد حساب ناقص |
| **ب. الملف الشخصي** | الشخص نفسه | نفسه | الوحيد الذي يجعل كلمة المرور سرًّا حقيقيًا |
| **ج. تعديل الحساب** | المدير | حساب قائم | لتدارك الـ٢٦ حسابًا القائمة |

### المسار (أ) — صفحتا الإنشاء

**صفحة إنشاء موظف** ([employees/actions.ts](../src/app/(dashboard)/main/(main)/employees/actions.ts) و`EmployeesClient`): الحقل الحالي «كلمة المرور» يبقى لكن يصير **اختياريًا**، ويُضاف حقل بريد. والتحقق `if (!name || !phone || !password)` يجب أن يسقط منه `password` — وإلا استحال إنشاء موظف بلا كلمة مرور.

**صفحة إنشاء مستخدم جمعية**: تكتسب الحقلين لأول مرة.

**قاعدة مشتركة:** بريد بلا كلمة مرور أو العكس = خطأ يُرفض. نصفهما لا يفتح شيئًا، ووجوده يوهم صاحبه أنه فعّل الدخول.

### المسار (ب) — الملف الشخصي

الحقل موجود اليوم ويقول «كلمة المرور (اختياري)». يُعاد استعماله بعد إضافة البريد بجانبه، **وبعد تصحيح الوصف**: هو اليوم يعِد بشيء لا يعمل.

### المسار (ج) — تدارك الحسابات القائمة

**هذا هو جواب سؤالك عن تحديث البريد للجمعيات والموظفين.**

لا حاجة لأداة هجرة منفصلة: صفحة تعديل الموظف وصفحة تعديل مستخدم الجمعية تكتسبان الحقلين، فيمرّ المدير على الـ٢٦ حسابًا ويعبّئها. ومن لم يُعبَّأ حسابه يبقى داخلًا بالجوال — بلا ضرر.

**وشاشة الموظفين تعرض عمودًا** يميّز من فعّل الدخول بالبريد ومن لم يفعّل، فيُعرف الباقي بنظرة لا بتخمين.

## ثالثًا: صفحة الدخول

### الشكل

مبدّل في الأعلى:

```
┌──────────────────┬──────────────────┐
│  البريد وكلمة    │   الجوال ورمز    │
│    المرور        │     التحقق       │
└──────────────────┴──────────────────┘
```

### حفظ الاختيار

`localStorage` بمفتاح `zad_login_method`. يُكتب عند كل تبديل، ويُقرأ عند التحميل فيُفتح آخر ما استُعمل.

**ولماذا لا يُحفظ في القاعدة:** هذا تفضيل **جهاز** لا تفضيل حساب. من يدخل من هاتفه بالـOTP ومن حاسبه بالبريد يجب أن يجد كل جهاز على ما تركه — ولو حُفظ على الحساب لتقاتل الجهازان على قيمة واحدة. وأيضًا: الاختيار يُقرأ **قبل** تسجيل الدخول، حين لا حساب بعد.

**دقّة تجنّب وميض الترطيب:** القراءة من `localStorage` تقع في المتصفح فقط، فالخادم لا يعرفها. تُقرأ عبر `useSyncExternalStore` أو بعد التركيب، وإلا اختلف ما يرسمه الخادم عمّا يرسمه المتصفح.

### الإجراءات الجديدة

```ts
loginWithEmployeeEmail(email, password)
loginWithCharityEmail(email, password)
```

كلاهما يبني نفس كوكي الجلسة الذي يبنيه مسار الـOTP اليوم — فلا يتغير شيء بعد الدخول: `getSession` والوسيط والحُرّاس تعمل كما هي.

## رابعًا: الأمن — ما يتغيّر بإضافة كلمة المرور

كلمة المرور تفتح بابًا لم يكن موجودًا: **التخمين**. الـOTP محميّ بأن الرمز يصل لهاتف لا يملكه المهاجم.

| الخطر | المعالجة |
|-------|----------|
| تخمين متكرر | `checkRateLimit` على `login-pw:${email}` وعلى IP |
| كشف البريد المسجَّل | رسالة واحدة «البريد أو كلمة المرور غير صحيحة» — لا تفرّق بين الحالتين |
| كلمة مرور ضعيفة | ٨ أحرف على الأقل، تُفحص في الخادم لا في المتصفح وحده |
| فرق التوقيت | `bcrypt.compare` دائمًا، حتى مع بريد غير موجود، على تجزئة وهمية |
| حساب معطَّل | فحص `isActive` قبل الدخول، كما يفعل مسار الـOTP |

> **قيد يجب أن تعرفه:** `checkRateLimit` يحفظ عدّاداته **في ذاكرة العملية**. على Vercel تعمل عدة نسخ، فالحد فعليًا أرخى مما يبدو. هذا قائم اليوم على الـOTP أيضًا، لكن التخمين يجعله أهم. علاجه جدول أو Redis — أقترح تأجيله وتسجيله، لا حلّه ضمن هذه الخطة.

## خامسًا: ترتيب التنفيذ

| # | الخطوة | لماذا هنا |
|---|--------|-----------|
| ١ | المخطط: البريد وكلمة المرور اختياريان للنموذجين | لا شيء يعمل قبله |
| ٢ | `hashPassword` و`verifyPassword` في `lib/` | نقطة واحدة للتجزئة والمقارنة |
| ٣ | إجراءا الدخول بالبريد + تحديد المعدل | الخادم قبل الواجهة |
| ٤ | صفحة الدخول: المبدّل وحفظ الاختيار | |
| ٥ | صفحتا الإنشاء + شاشتا التعديل (موظف/جمعية) | **قبل** الخطوة ٧ |
| ٦ | الملف الشخصي: بريد + كلمة مرور بوصف صحيح | |
| ٧ | تعبئة الـ٢٦ حسابًا، ثم `UPDATE … SET password = NULL` | آخر خطوة تمسّ بيانات |
| ٨ | عمود «الدخول بالبريد» في شاشة الموظفين | لمتابعة ما تبقّى |

**الخطوة ٧ آخر شيء عمدًا.** محو التجزئات قبل أن يعمل مسار الضبط يترك الجميع بلا كلمة مرور ولا وسيلة لوضع واحدة.

## سادسًا: التحقق قبل الإعلان

- [ ] موظف بلا بريد يدخل بالجوال كما كان — **لا انحدار**
- [ ] موظف ببريد وكلمة مرور يدخل بالطريقتين
- [ ] بريد صحيح وكلمة مرور خاطئة ← رسالة عامة لا تكشف أيهما
- [ ] حساب معطَّل يُرفض في المسارين
- [ ] بريد مكرر يُرفض عند الحفظ برسالة مفهومة
- [ ] الاختيار يبقى محفوظًا بعد إغلاق المتصفح
- [ ] لا وميض بين ما يرسمه الخادم وما يرسمه المتصفح على صفحة الدخول
- [ ] مستخدم جمعية بالطريقتين، ثم اختيار الجمعية يعمل بعدهما

## قرارات أحتاجها منك

1. **البريد إلزامي على الحسابات الجديدة أم اختياري؟** أرشّح **إلزاميًا للجديدة** (فلا تتراكم حسابات ناقصة) و**اختياريًا للقائمة** (فلا يُقفل أحد).
2. **هل يعدّل الموظف بريده بنفسه؟** أرشّح **لا** — البريد هو الهوية، وتغييره بيد المدير. وكلمة المرور بيد صاحبها وحده.
3. **حدّ التخمين:** أرشّح ٥ محاولات كل ١٥ دقيقة لكل بريد.
4. **مستخدمو الجمعيات:** هل يدخلون بالبريد أيضًا أم يبقون على الـOTP؟ فهمت من طلبك أنهم يشملهم، وبنيت الخطة على ذلك — أكّد لي.

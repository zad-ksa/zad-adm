# نقل قاعدة البيانات من سيدني إلى مومباي

خطة تنفيذ. اقرأها كاملة قبل أن تبدأ، ولا تبدأ الخطوة ٤ إلا وأنت مستعدّ لتوقّف قصير.

---

## لماذا

قياس فعلي من الرياض (زمن الذهاب والإياب، وسيط ٥ محاولات):

| المنطقة | الزمن |
|---|---|
| سيدني `ap-southeast-2` — **الحالي** | **٢٦١ مللي** |
| مومباي `ap-south-1` — **الهدف** | **٨٦ مللي** |
| فرانكفورت `eu-central-1` — بديل | ١٠٣ مللي |

كل انتقال بين صفحتين يدفع رحلتين (طلب + استجابة)، فالتوفير **~٣٥٠ مللي لكل نقرة**.

> **القاعدة التي لا تُكسر:** منطقة Vercel ومنطقة Supabase **تتحركان معاً**.
> نقل القاعدة وحدها يجعل الوضع **أسوأ** لا أفضل: الصفحة الواحدة تقوم بعدة رحلات
> بين الدالة والقاعدة، فتفريقهما يضرب المسافة في عددها.

---

## ما تنقله فعلاً (تحقّقنا منه)

| البند | الحالة |
|---|---|
| حجم القاعدة | **١٦ ميغابايت** |
| عدد الجداول | ٦٢ (مخطط `public` فقط) |
| نسخة Postgres | **17.6** |
| Supabase Auth | **صفر مستخدم** — مصادقتك بـ `jose` وجداولك |
| Supabase Storage | **صفر ملف** — ملفاتك في Cloudinary |
| مكتبة `@supabase/*` | **غير مستعملة** في الكود |
| الامتدادات | `pgcrypto` · `uuid-ossp` · `pg_stat_statements` · `supabase_vault` |

أي أنك تنقل قاعدة Postgres عادية صغيرة، لا منظومة Supabase كاملة.

---

## قبل أن تبدأ

### ١. ثبّت أدوات Postgres 17

`pg_dump` **غير مثبَّت على جهازك** — تحققنا. ولا يكفي أي إصدار: أداة أقدم من
الخادم ترفض العمل، وخادمك على **17.6**.

- **Windows:** حمّل مثبّت PostgreSQL 17 من postgresql.org واختر
  *Command Line Tools* فقط (لا تحتاج الخادم نفسه).
- تحقّق: `pg_dump --version` يجب أن يظهر **17.x** أو أحدث.

### ٢. تأكد أن مومباي متاحة في Vercel

Vercel يسمّي مومباي `bom1`. افتح مشروعك ← **Settings ← Functions ← Region**
وتأكد من وجودها **قبل** أن تنشئ مشروع Supabase.

إن لم تجدها، استعمل **فرانكفورت** في الاثنين (`eu-central-1` في Supabase،
`fra1` في Vercel). الفرق ١٧ مللي فقط، والتوفّر أهم.

### ٣. مرّر قائمة مناطق Supabase كاملة

القائمة مقصوصة في الواجهة. مرّر لأعلى ولأسفل وابحث عن **الإمارات
`me-central-1`** — قِسناها بـ**٥٧ مللي**، أسرع من مومباي. إن وُجدت (وvercel
يدعمها) فهي الخيار الأفضل.

### ٤. اختر وقتاً هادئاً

بين أخذ النسخة وتبديل الرابط، **أي كتابة على القاعدة القديمة تضيع**. ١٦ ميغابايت
تُنقل في دقائق، لكن أعلن توقفاً قصيراً وتأكد أن لا أحد يستعمل النظام.

## التنفيذ

### الخطوة ١ — أنشئ المشروع الجديد

من لوحة Supabase: **New Project** ← المنطقة **South Asia (Mumbai) `ap-south-1`**.

احتفظ برابطي الاتصال من **Settings ← Database**:

- **Connection pooling** (المنفذ `5432` أو `6543`) ← سيصبح `DATABASE_URL`
- **Direct connection** (`db.xxxx.supabase.co`) ← سيصبح `DIRECT_URL`

> مشروعك يستعمل **الاثنين**. لا تنسَ الثاني.

### الخطوة ٢ — خُذ النسخة

```bash
pg_dump "<الرابط المباشر القديم>" \
  --schema=public \
  --no-owner \
  --no-privileges \
  --file=zad-backup.sql
```

**استعمل الرابط المباشر** (`db.makxgdhadxgleyambiqz.supabase.co`) لا الـ pooler —
الـ pooler لا يدعم عمليات النسخ الطويلة بشكل موثوق.

**`--schema=public` مقصود:** يتجاوز مخططات `auth` و`storage` و`realtime` التي
ينشئها Supabase بنفسه في أي مشروع جديد. نسخها يسبّب تعارضات، وأنت لا تستعملها.

تحقّق قبل المتابعة:

```bash
# يجب أن يكون بضعة ميغابايت، لا صفراً
ls -lh zad-backup.sql
grep -c "CREATE TABLE" zad-backup.sql   # المتوقّع: 62
```

### الخطوة ٣ — استعِد في الجديد

```bash
psql "<الرابط المباشر الجديد>" --file=zad-backup.sql
```

تحذيرات عن `extension already exists` طبيعية ولا تضرّ. **الأخطاء الحقيقية**
(`ERROR:`) تعني توقّفاً وتحقيقاً قبل المتابعة.

### الخطوة ٤ — بدّل الروابط

**محلياً في `.env`:**

```
DATABASE_URL=<رابط pooler الجديد>
DIRECT_URL=<الرابط المباشر الجديد>
```

**في Vercel** (Settings ← Environment Variables): بدّل المتغيّرين نفسيهما.

> **لا تلمس بقية المتغيّرات.** خصوصاً هذين:
>
> - **`DONOR_ACCOUNT_ENC_KEY`** — حسابات المتبرعين مشفّرة به. تغييره يجعل
>   البيانات المنقولة **غير قابلة للفك نهائياً**.
> - **`JWT_SECRET`** — تغييره يُخرج كل المستخدمين من جلساتهم.
>
> وكذلك `CRON_SECRET` و`CLOUDINARY_*` و`AUTHENTICA_API_KEY` — انسخها كما هي.

### الخطوة ٥ — بدّل منطقة Vercel

**Settings ← Functions ← Region ← Mumbai (bom1)**، ثم **أعد النشر**. تغيير
المنطقة لا يسري على النشر القائم.

### الخطوة ٦ — طابِق المخطط

مشروعك يُدار بـ `db push` لا بملفات ترحيل، فتأكد أن القاعدة الجديدة مطابقة:

```bash
npx prisma db push
```

**المتوقّع:** `Your database is already in sync with your Prisma schema`.
لو اقترح تغييرات، فالنسخة ناقصة — **توقّف وحقّق** قبل القبول.

## التحقق بعد النقل

### أ. عدّ الصفوف — قارن بالقديم

شغّل هذا على **الاثنين** وقارن:

```sql
select 'Employee' t, count(*) from "Employee"
union all select 'Request', count(*) from "Request"
union all select 'RequestLog', count(*) from "RequestLog"
union all select 'Charity', count(*) from "Charity"
union all select 'CharityUser', count(*) from "CharityUser"
union all select 'DesignRequest', count(*) from "DesignRequest"
union all select 'Meeting', count(*) from "Meeting"
union all select 'AttendanceRecord', count(*) from "AttendanceRecord"
order by 1;
```

### ب. الفهارس المهمة موجودة

```sql
select tablename, indexname from pg_indexes
where schemaname = 'public'
  and indexname in (
    'RequestLog_actorId_action_idx',
    'Request_delegatedToId_idx',
    'AttendanceRecord_charityUserId_charityId_workDate_key',
    'AttendanceRecord_charityId_autoClosedAt_idx'
  )
order by 1;
```

يجب أن تظهر **الأربعة**. غيابها يعني نسخة ناقصة، وبعضها أمني لا أدائي فقط.

### جـ. اختبار وظيفي على المعاينة

- سجّل دخولاً — يتحقق من `JWT_SECRET` والجلسات
- افتح **الاعتمادات** — يتحقق من العزل والفهارس
- افتح **حسابات المتبرعين** — يتحقق من `DONOR_ACCOUNT_ENC_KEY`
- ارفع **طلب تصميم** — يتحقق من Cloudinary وأنواع التصاميم
- افتح **الموارد البشرية ← الإعدادات** — يتحقق من جداول الحضور

### د. قِس المكسب

```bash
node -e "const n=require('net');const t=Date.now();const s=n.createConnection({host:'<مضيف القاعدة الجديدة>',port:5432},()=>{console.log(Date.now()-t,'مللي');s.end()})"
```

**المتوقّع: ~٨٦ مللي بدل ٢٦١.**

## التراجع

النقل قابل للعكس ما دامت القاعدة القديمة قائمة:

1. أعِد `DATABASE_URL` و`DIRECT_URL` إلى قيمتيهما القديمتين (محلياً وفي Vercel)
2. أعِد منطقة Vercel إلى `syd1`
3. أعد النشر

**لا تحذف المشروع القديم قبل أسبوع** من التشغيل السليم. تكلفة إبقائه أرخص
بكثير من اكتشاف نقص بعد الحذف.

**البيانات المكتوبة على الجديد بعد التبديل تضيع عند التراجع** — لهذا التحقق
يكون فوراً لا بعد يومين.

---

## أشياء **لا** تحتاج تغييراً

- **Cloudinary** — الملفات مستقلة عن القاعدة تماماً
- **المهمة المجدولة** في `vercel.json` — تتبع النشر لا القاعدة
- **الكود** — لا سطر واحد يتغيّر؛ النقل كله في متغيّرات البيئة والإعدادات

---

## بديل بلا نقل

Supabase تتيح **Read Replicas** في مناطق أخرى (ميزة مدفوعة). تطبيقك قراءاته
أكثر من كتاباته بكثير، فنسخة قراءة في مومباي قد تعطي معظم الفائدة **بلا توقّف
ولا نقل**.

لم نتحقق من توفّرها في خطتك الحالية ولا من سعرها — يستحق السؤال قبل اتخاذ
قرار النقل الكامل.

## فرضية تستحق المراجعة

هذه الخطة مبنية على أن **مستخدميك كلهم في السعودية**. لو كان بينهم من هو في
آسيا أو أوروبا فقد تتغيّر المنطقة المثلى — أعد القياس من مواقعهم قبل التنفيذ.

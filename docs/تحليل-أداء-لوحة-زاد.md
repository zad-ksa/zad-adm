# أداء لوحة موظفي زاد — أين يذهب الوقت فعلًا

فحص لـ46 مسارًا تحت `/main`، وقياسات على قاعدة بيانات الإنتاج.

التاريخ: 2026-08-26

---

## القياس الذي يحكم كل شيء

قبل أي توصية، قِسْت الفرق بين زمن الشبكة وزمن الاستعلام، لأن الخلط بينهما يقلب الأولويات:

| القياس | القيمة |
|--------|--------|
| زمن الرحلة من جهاز في السعودية إلى `ap-southeast-2` | **296ms** (وسيط ٩ محاولات) |
| تنفيذ `SELECT * FROM "Task" ORDER BY "createdAt"` داخل Postgres نفسه | **0.65ms** |
| حجم قاعدة البيانات كاملة | 16 ميجابايت |
| أكبر جدول | `ServiceStageStep` بـ422 صفًا |

الاستعلامات شبه مجانية. **الوقت كله في عدد الرحلات، لا في ثقل الاستعلام.**

ولهذا نتيجة عملية مهمة: في الإنتاج تكون الدالة وقاعدة البيانات في المنطقة نفسها (رحلة ~1-2ms)، فاستعلام مثل الذي أعلاه يكلّف **~3ms لا 948ms** كما يظهر من جهازك. أي أن جزءًا كبيرًا مما يبدو بطيئًا أثناء التطوير ليس بطيئًا للمستخدم.

ما **لا** يتقلص بالمنطقة: الرحلات بين متصفح المستخدم والخادم، وحجم ما يُنقل فيها. وهناك تحديدًا يقع البطء الحقيقي.

## ١. استعلام قاعدة بيانات في كل طلب، قبل أن تبدأ الصفحة

### الملاحظة

[proxy.ts:37](../src/proxy.ts#L37):

```ts
export default async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;
  const session = await getSession();   // ← يقرأ من قاعدة البيانات
```

و`getSession` تنفّذ `employee.findUnique` للتحقق من `isActive` والصلاحيات ([auth.ts:107](../src/lib/auth.ts#L107)).

### لماذا هذا مكلف

- **`proxy` في Next 16 يعمل على Node.js runtime افتراضيًا** — لا Edge. الوثائق المرفقة تنص على ذلك في [proxy.md:219](../node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md#L219). فالاستعلام حقيقي وليس متجاوَزًا.
- يعمل على **كل** طلب يطابق `/main/:path*`: كل تنقّل بين التبويبات (طلب RSC)، وكل `server action`، وكل نبضة استطلاع دوري.
- وهو **متسلسل قبل** أن يبدأ المسار أصلًا — لا شيء يبدأ حتى يعود.
- ثم يستدعي `layout` الدالة `getSession()` مرة أخرى. `cache()` من React تُلغي التكرار داخل عملية رسم واحدة، **والوسيط ليس جزءًا من تلك العملية** — فالاستعلام يتكرر في كل تحميل صفحة.
- والملف يفكّ تشفير الكوكي مرتين أيضًا: مرة داخل `getSession` ومرة في `refreshSessionCookie`.

ووثائق Next صريحة في التحذير من هذا بالذات ([16-proxy.md:29](../node_modules/next/dist/docs/01-app/01-getting-started/16-proxy.md#L29)):

> Proxy is _not_ intended for slow data fetching. While Proxy can be helpful for **optimistic checks** such as permission-based redirects, it should not be used as a full session management or authorization solution.

### لماذا الحل آمن

الوسيط لا يحتاج القاعدة أصلًا. كل ما يقرره هو إعادة توجيه من لا يملك جلسة، وحمولة الـJWT وحدها تكفي لذلك. والتحقق الحقيقي — أن الموظف ما زال نشطًا وأن صلاحياته الحالية هي هذه — يقع بعد ذلك في التخطيط، وهو موجود فعلًا في الموضعين:

- [(dashboard)/layout.tsx:14](<../src/app/(dashboard)/layout.tsx#L14>) — `if (!session) redirect("/")`
- [portal/[name]/layout.tsx:18](../src/app/portal/[name]/layout.tsx#L18) — نفس الحارس

فموظف عُطّل حسابه سيمر من الوسيط ثم يُرفض في التخطيط ويُعاد توجيهه. **لا يُفقد أي ضمان أمني** — وهذا بالضبط ما تعنيه الوثائق بـ optimistic check في الوسيط والتحقق الفعلي في طبقة البيانات.

### الحل

```ts
// في proxy.ts — فحص متفائل بلا قاعدة بيانات
export default async function middleware(request: NextRequest) {
  const { pathname } = request.nextUrl;

  const raw = request.cookies.get("session")?.value;
  let payload: Record<string, unknown> | null = null;
  if (raw) {
    try {
      payload = await decrypt(raw);
    } catch {
      payload = null; // منتهية أو تالفة
    }
  }

  if (pathname.startsWith("/main") && !payload) {
    return NextResponse.redirect(new URL("/", request.url));
  }

  if (pathname.startsWith("/portal/") && payload && payload.userType !== "CHARITY_USER") {
    return NextResponse.redirect(new URL("/main", request.url));
  }

  const response = NextResponse.next();
  if (payload) refreshSessionCookie(payload, response); // يستقبل الحمولة المفكوكة بدل فكّها ثانية
  return response;
}
```

الأثر: **رحلة قاعدة بيانات كاملة تختفي من كل طلب**، وفكّ تشفير مكرر يختفي معها.

## ٢. صفحة البريد فيها رحلتان مبرمجتان

### الملاحظة

```tsx
useEffect(() => {
  fetchMails();          // ← الرسائل تُطلب بعد التركيب، لا مع الصفحة
}, [currentTab, page, appliedSearch]);
```

### لماذا هذا مكلف

التسلسل الذي يعيشه المستخدم:

```
ضغط على «البريد»
  └─ طلب RSC إلى سيدني ......... ~300ms   ← يصل الهيكل + قائمة الموظفين
      └─ تركيب المكوّن
          └─ إجراء خادم getInbox .. ~300ms   ← الآن فقط تصل الرسائل

```

**ضِعف ما يلزم.** وهذا بالضبط وصف ما لاحظته سابقًا: «ينتقل التبويب ثم تبقى الصفحة قليلًا قبل أن تظهر علامة التحميل».


## ٣. لا يوجد `staleTimes` — ذاكرة الموجّه معطّلة عمليًا

### الملاحظة

[next.config.ts](../next.config.ts) لا يضبط `experimental.staleTimes`. والافتراضي منذ Next 15 هو `dynamic: 0` كما في [staleTimes.md](../node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/staleTimes.md):

> - The `dynamic` property is used when the page is neither statically generated nor fully prefetched.
>   - Default: 0 seconds (not cached)

وكل مسارات اللوحة الـ46 ديناميكية (`ƒ` في مخرجات البناء).

### لماذا هذا مكلف

مقاطع الصفحات **لا تُعاد من الذاكرة إطلاقًا**. الانتقال من البريد إلى الاعتمادات ثم العودة للبريد يعيد الجلب من سيدني كاملًا — رغم أنك كنت هناك قبل ثوانٍ.

### الحل

```ts
// next.config.ts
const nextConfig: NextConfig = {
  experimental: {
    serverActions: { bodySizeLimit: "50mb" },
    staleTimes: {
      dynamic: 30,   // العودة لتبويب زرته خلال 30 ثانية تصير فورية
      static: 180,
    },
  },
  // ...
};
```

٣٠ ثانية اختيار متحفّظ يناسب بيانات اللوحة. والصفحات التي يجب أن تبقى طازجة دائمًا (الاعتمادات) تُحدَّث باستطلاعها الدوري على أي حال.

> تنبيه من الوثائق نفسها: هذا **لا** يمس التصيير الجزئي — التخطيطات المشتركة لا يُعاد جلبها مع كل تنقّل أصلًا، بل المقطع المتغيّر فقط.

## ٥. الجلب المتسلسل والاستعلامات غير المحدودة

### الملاحظة

مسح آلي على الصفحات الـ46:

| المؤشر | العدد |
|--------|-------|
| صفحات تستخدم `Promise.all` | **12 من 46** |
| صفحات تجلب بالتسلسل | **34** |
| استدعاءات `findMany` بلا `take` | **48** |

أثقلها [tasks/page.tsx](<../src/app/(dashboard)/main/(main)/tasks/page.tsx>): ست استعلامات **مستقلة تمامًا** تُنفَّذ واحدًا بعد الآخر — الموظفون، الجمعيات، المهام، الإنجازات، المهام الدائمة، التصنيفات.

### قدر المشكلة بصدق

بالأرقام المقيسة: ٦ استعلامات × ~3ms = **~18ms في الإنتاج**. لن يشعر بها أحد.

فهذا **ليس** عنق الزجاجة اليوم، وأُدرجه لسببين مختلفين تمامًا:

**أ. خطر التوسّع.** `prisma.task.findMany()` بلا `take` تجلب كل مهمة أُنشئت منذ بدء النظام، مع كل تحديثاتها. اليوم ١٤٦ صفًا. عند ٥٠٠٠ لن تكون ٣ms.

**ب. حجم الحمولة — وهذه مشكلة حقيقية الآن.** قِسْتها:

```
tasks page — task.findMany (كل المهام مع التحديثات): 146 صفًا
tasks page — charity.findMany (كل الأعمدة):            9 صفوف
JSON المُرسَل إلى المتصفح:                          102 كيلوبايت
```

١٠٢ كيلوبايت تعبر المحيط في كل زيارة للصفحة. **هذا لا يتقلص بتغيير منطقة قاعدة البيانات** لأنه بين الخادم والمتصفح، لا بين الخادم والقاعدة.

### الحل

```ts
// tasks/page.tsx — التوازي أولًا
const taskFilter = hasViewAllTasks ? {} : { assignedToId: session.id };

const [employees, charities, initialTasks, initialAchievements, initialPermanentTasks, categories] =
  await Promise.all([
    prisma.employee.findMany({
      where: { isActive: true },
      select: { id: true, name: true, phone: true, role: true, avatarUrl: true },
      orderBy: { name: "asc" },
    }),
    // كانت تجلب كل عمود في كل جمعية بلا حاجة
    prisma.charity.findMany({
      select: { id: true, name: true, logoUrl: true },
      orderBy: { name: "asc" },
    }),
    prisma.task.findMany({
      where: taskFilter,
      orderBy: { createdAt: "desc" },
      take: 100,                                    // ← حد أعلى
      include: { updates: { orderBy: { createdAt: "asc" }, take: 20 } },
    }),
    prisma.achievement.findMany({
      where: hasViewAllTasks ? {} : { employeeId: session.id },
      orderBy: { createdAt: "desc" },
      take: 100,
    }),
    prisma.permanentTask.findMany({
      where: taskFilter,
      orderBy: { createdAt: "desc" },
      take: 100,
      include: { assignedTo: { select: { id: true, name: true, avatarUrl: true } } },
    }),
    getCategories(),
  ]);
```

الفرع الشرطي `if (hasViewAllTasks)` انطوى في `where` بدل تكرار الاستعلامات الثلاثة مرتين.

ونفس المعالجة تُطبَّق على البقية بالترتيب: `governance/[name]`، `strategy/[name]`، `services-overview`، `finance/[name]`، `programs/[name]`.

```tsx
// ١) فترة أطول — ١٥ ثانية سخية لطلبات اعتماد لا تتغير بهذا الإيقاع
const POLL_MS = 60000;

// ٢) استعلام خفيف يسأل «هل تغيّر شيء؟» بدل جلب كل شيء

export async function getRequestsVersion() {
```

## ما فحصته ولم أجده مشكلة

من الإنصاف تسجيل النتائج السالبة:

- **الفهارس سليمة.** المسوح التسلسلية على `Request` و`Task` اختيار صحيح من Postgres عند هذه الأحجام (56–422 صفًا)، لا نقص فهرسة. إضافة فهارس الآن لن تُسرّع شيئًا.
- **التخطيطات لا يُعاد جلبها مع كل تنقّل.** ظننتُ في البداية أن الاستعلامات الأربعة المتسلسلة في [(dashboard)/layout.tsx](<../src/app/(dashboard)/layout.tsx>) تُدفع في كل انتقال، والوثائق تنفي ذلك صراحة: *"shared layouts won't automatically be refetched on every navigation, only the page segment that changes"*. فهي كلفة تحميل أول لا كلفة تنقّل — ويبقى ترتيبها بـ`Promise.all` تحسينًا مفيدًا لأول تحميل، لكنه ليس عاجلًا.
- **صفحة الاعتمادات مُحسَّنة فعلًا** — `Promise.all` مع تعليق يشرح السبب، ولا تُعيد جلب ما أرسله الخادم عند التركيب.
- **لا تسريب استعلامات N+1** وجدته في الصفحات التي فحصتها.

## ملاحظة على منهج القياس

كل الأرقام هنا من قاعدة بيانات الإنتاج، لكن **زمن الشبكة فيها من جهاز في السعودية إلى سيدني**، لا من دالة Vercel في سيدني. حيثما ذكرتُ زمنًا للإنتاج، فصلتُ زمن التنفيذ داخل Postgres (بـ`EXPLAIN ANALYZE`) عن زمن الرحلة (بقياس `SELECT 1` تسع مرات) وأضفتُ إليه رحلة داخل المنطقة تقديرًا. الأرقام التي **لا** تحتاج هذا التصحيح هي أحجام الحمولات وأعداد الصفوف وإحصاءات `pg_stat_user_tables` — فهي مستقلة عن موقع القياس.

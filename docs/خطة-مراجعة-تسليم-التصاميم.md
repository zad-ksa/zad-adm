# خطة — مراجعة الجمعية بعد التسليم، وطلبات شركة زاد

التاريخ: 2026-08-27

خطة تنفيذية لطلبين: دورة مراجعة بعد إنهاء طلب التصميم، وإتاحة «شركة زاد» كجهة تابعة.

---

## الوضع الحالي

قرأت الكود قبل الخطة. ما يحدث اليوم عند الضغط على «إنهاء» في [designRequests.ts](../src/app/actions/designRequests.ts):

1. تُحذف **مرفقات الطلب** (`BRIEF`) من Cloudinary فورًا — بلا رجعة.
2. تُحذف صفوفها من القاعدة.
3. تُضاف الملفات النهائية (`DELIVERABLE`).
4. الحالة تصير `COMPLETED`.

أي أن التسليم **نهائي في اللحظة نفسها**، ولا دور للجمعية فيه إطلاقًا. وحذف المرفقات يقع قبل أن يراها أحد.

وحقل `charityId` **إلزامي** في `DesignRequest` ومربوط بجدول `Charity` — فلا يمكن اليوم إنشاء طلب لا يتبع جمعية.

---

## أولًا: دورة المراجعة بعد التسليم

### التدفق المطلوب

```
موظف زاد يضغط «إنهاء»
   └─ الطلب ← «بانتظار مراجعة الجمعية»   (المرفقات تبقى كما هي)
      └─ تبدأ 24 ساعة
         ├─ (١) الجمعية تعتمد نهائيًا    → منجز + حذف المرفقات + إبقاء الملف النهائي
         ├─ (٢) الجمعية تُعيده بملاحظات  → «قيد التعديل» + 24 ساعة من تاريخ الإعادة
         │                                  (خارج ترتيب التنفيذ)
         │        └─ زاد تُنهيه ثانيةً → يعود إلى «بانتظار المراجعة» بـ24 ساعة جديدة
         └─ (٣) تمر 24 ساعة بلا ردّ      → اعتماد تلقائي (نفس أثر ١)
```

### الحالات الجديدة

| الحالة | المعنى | في ترتيب التنفيذ؟ |
|--------|--------|--------------------|
| `AWAITING_REVIEW` | سُلّم وينتظر ردّ الجمعية | **لا** |
| `REVISION_REQUESTED` | أُعيد بملاحظات، زاد تعدّل | **لا** |

`computeSchedule` يحسب صفوف `PENDING` وحدها، فالحالتان الجديدتان تخرجان من الترتيب **تلقائيًا** — وهذا يحقق شرط «خارج عن جدول أدوار الطلبات» بلا كود إضافي.

### تغييرات المخطط

```prisma
enum DesignRequestStatus {
  PENDING
  COMPLETED
  UNDER_REVIEW
  REJECTED
  AWAITING_REVIEW      // ملحقة في الآخر
  REVISION_REQUESTED
}

model DesignRequest {
  // ...
  /// متى سُلّم آخر مرة — منه تُحسب الـ24 ساعة.
  deliveredAt        DateTime?
  /// متى أُعيد بملاحظات — منه تُحسب مهلة التعديل.
  revisionRequestedAt DateTime?
  /// هل اعتُمد بمرور المهلة لا بفعل الجمعية؟ يُعرض للطرفين.
  autoApproved       Boolean  @default(false)
}

/// جولة تعديل واحدة: ملاحظات الجمعية وتاريخها.
model DesignRequestRevision {
  id        String   @id @default(uuid())
  requestId String
  request   DesignRequest @relation(fields: [requestId], references: [id], onDelete: Cascade)
  notes     String   @db.Text
  createdAt DateTime @default(now())
  @@index([requestId])
}
```

**لماذا جدول للملاحظات لا حقل نصّي:** الإعادة قد تتكرر أكثر من مرة، وحقل واحد يُكتب فوقه يمحو ما طُلب في الجولة السابقة — فتضيع الحجة عند الخلاف. والجدول يوازي `DesignRequestExtension` القائم.

**إلحاق قيم التعداد في الآخر** لا في ترتيبها المنطقي: إضافة قيمة إلى نوع تعداد في Postgres رخيصة، وإعادة الترتيب تستلزم إعادة بناء النوع على بيانات حيّة.

### تعديل «الإنهاء»

`markDesignRequestComplete` يتوقف عن كونه نهائيًا:

- **لا يحذف** أي مرفق.
- يضيف الملفات النهائية.
- الحالة ← `AWAITING_REVIEW`، و`deliveredAt = now()`.

وحذف المرفقات ينتقل إلى نقطة واحدة جديدة تُستدعى من ثلاثة مسارات (اعتماد الجمعية، الاعتماد التلقائي، وأي مسار مستقبلي):

```ts
/** نهاية الطريق: تحذف مرفقات الطلب من Cloudinary وتُبقي الملف النهائي. */
async function finalizeDesignRequest(id: string, opts: { auto: boolean })
```

### إجراءات جديدة

| الإجراء | من يستدعيه | الأثر |
|---------|------------|-------|
| `approveDeliveryByCharity(id)` | الجمعية | `COMPLETED` + حذف المرفقات |
| `requestRevision(id, notes, removeAttachmentIds, addAttachments)` | الجمعية | `REVISION_REQUESTED` + `revisionRequestedAt` + صفّ ملاحظات |

`requestRevision` يقبل حذف مرفقات قديمة وإضافة جديدة — تمامًا كنموذج إعادة الرفع الذي بنيناه للطلبات المرفوضة، ويعيد استعمال المنطق نفسه.

### الاعتماد التلقائي بعد 24 ساعة

مسار كرون جديد `/api/cron/design-auto-approve`، على نمط `attendance-close` القائم: يفشل مغلقًا إن غاب `CRON_SECRET`.

```json
{ "path": "/api/cron/design-auto-approve", "schedule": "0 * * * *" }
```

**كل ساعة لا كل يوم.** المهلة 24 ساعة، وفحص يومي واحد يجعل الاعتماد يقع بعد 24–48 ساعة حسب لحظة التسليم — أي أن نصف الحالات تخالف ما وُعدت به الجمعية.

يعتمد كل طلب `AWAITING_REVIEW` مضى على `deliveredAt` أكثر من 24 ساعة، ويضع `autoApproved = true`.

**سؤال يحتاج قرارك:** ماذا عن طلب في `REVISION_REQUESTED` مضت مهلته دون أن تُنهيه زاد؟ الحالات الثلاث التي وصفتَها تغطي صمت **الجمعية** لا صمت **زاد**. أرشّح تركه كما هو (ينتظر زاد بلا حدّ، ويظهر متأخرًا) لأن الاعتماد التلقائي هنا يكافئ التقصير. أخبرني إن أردت غير ذلك.

### الواجهات

**عند الجمعية** — تبويب جديد «بانتظار مراجعتك» مع عدّاد، وعلى البطاقة:
- الملفات النهائية للتحميل
- زر **«اعتماد نهائي»** (بتأكيد: المرفقات ستُحذف)
- زر **«إعادة للتعديل»** يفتح نموذجًا: ملاحظات إلزامية + المرفقات القديمة قابلة للحذف + رفع جديد
- عدّاد للوقت المتبقي من الـ24 ساعة

**عند موظف زاد** — تبويب «قيد التعديل» مع عدّاد، وملاحظات الجمعية معروضة على البطاقة، وزر «إنهاء» يعيدها إلى `AWAITING_REVIEW`.

**الألوان:** `AWAITING_REVIEW` و`REVISION_REQUESTED` تُضافان إلى `getDesignRequestProgress`. الأولى محايدة (لا عدّاد تسليم)، والثانية تعرض ما تبقى من مهلة التعديل.

## ثانيًا: «شركة زاد» كجهة تابعة

### التغيير

`charityId` يصير اختياريًا. `null` تعني **الطلب لشركة زاد نفسها**.

```prisma
charityId String?
charity   Charity? @relation(fields: [charityId], references: [id], onDelete: Cascade)
```

**لماذا `null` لا سجل جمعية باسم «شركة زاد»:** السجل الوهمي يظهر في كل قائمة جمعيات في الموقع — الحوكمة والاستراتيجية والعقود والموارد البشرية — ويحتاج استثناءً في كل واحدة منها. و`null` تعبّر عن الغياب مرة واحدة في المكان الذي يعنيه.

### ما يلزم مراجعته

بحثت عن المواضع التي تفترض وجود جمعية، وهي **١٢ موضعًا** في `designRequests.ts` وحده:

| النمط | العدد | المعالجة |
|-------|-------|----------|
| `revalidatePath("/portal/${charity.name}/...")` | ٥ | تُتخطّى عند `null` — لا بوابة لشركة زاد |
| `notifyDesignStaff(charity.name, ...)` | ٢ | «شركة زاد» بدل الاسم |
| `include: { charity: { select: { name } } }` | ٣ | يصير النوع قابلًا لـ`null` والمترجم يقود بقية التعديل |
| `charityName` في البطاقة | ٢ | «شركة زاد» عند الغياب |

**والترتيب:** `computeSchedule` يجمع حسب `charityId`، و`null` تُشكّل طابورًا مستقلًا لشركة زاد — وهو السلوك الصحيح: طلبات زاد الداخلية لا تزاحم طلبات الجمعيات.

### الواجهة

في نموذج موظف زاد، قائمة الجهة تكتسب خيارًا أول:

```
— شركة زاد —
الجمعية أ
الجمعية ب
```

وقيمته سلسلة فارغة تُترجم إلى `charityId: null`. والتحقق الحالي `if (!input.charityId) return { error: "يرجى اختيار الجمعية" }` **يجب أن يُعدَّل**، وإلا منع خيار زاد — وهذه أسهل نقطة يسهو عنها التنفيذ.

**ولا يظهر الخيار في بوابة الجمعيات** — الجمعية لا ترفع طلبًا باسم زاد.

## المخاطر

| الخطر | المعالجة |
|-------|----------|
| **الطلبات القائمة** حالتها `COMPLETED` ومرفقاتها محذوفة أصلًا | لا تتأثر: التدفق الجديد يبدأ من الإنهاء القادم. `deliveredAt` تبقى `null` فيها، والكرون يتجاهل ما ليس `AWAITING_REVIEW` |
| فقدان المرفقات عند إعادة التعديل | الحذف صار في نقطة واحدة تُستدعى عند الاعتماد النهائي فقط |
| الكرون يعتمد طلبًا اعتمدته الجمعية لتوّها | يُفلتر بالحالة `AWAITING_REVIEW` وقت التنفيذ، فالسباق يخسره الكرون |
| `charityId = null` يكسر استعلامًا لم أنتبه له | المترجم يمسك أغلبها بعد تغيير النوع؛ سأمرّ على `tsc` قبل أي شيء آخر |

## قرارات أحتاجها منك قبل البدء

1. **صمت زاد في `REVISION_REQUESTED`** — تُترك بلا مهلة (ترشيحي)، أم يُعتمد الطلب تلقائيًا أيضًا؟
2. **من يملك حق الاعتماد النهائي في الجمعية؟** أرشّح `create_design_requests` نفسها التي ترفع الطلب. أم صلاحية منفصلة؟
3. **عدد جولات التعديل** — بلا حدّ (ترشيحي)، أم سقف؟
4. **إشعار الجمعية بالتسليم** — لا يوجد اليوم نظام إشعارات لمستخدمي الجمعيات (`AppNotification` للموظفين فقط). فالجمعية تعرف بالدخول للصفحة. هل يكفي، أم نضيف إشعارات للجمعيات (تغيير مخطط أوسع)؟
